# 火车票预订系统 — 性能测试方案

## 1. 测试目标

1. 通过阶梯加压找到系统性能拐点，给出单实例在**当前配置下**可支撑的并发量
2. 验证查询、混合（查询+下单）场景的 TPS、平均/P90/P95/P99 响应时间、错误率
3. 验证同一座位并发下单不超卖、不丢单
4. 通过 JProfiler CPU 采样与资源监控定位瓶颈，给出优化与负压（限流/降级）方案

> 本方案的目标不是证明“系统容量”，而是给出可复现的测量口径。容量结论必须带上配置条件（连接池、缓存、数据规模、是否同机压测）。

## 2. 测试范围

| 场景 | 接口 | 读/写 | 说明 |
|------|------|-------|------|
| 查询（会话复用） | `POST /trains/search` | 读 | 登录一次，循环查询；用于阶梯加压 |
| 登录+查询 | `GET/POST /login`、`POST /trains/search` | 读 + 登录 | 每次迭代重新登录，用于对比 BCrypt 代价 |
| 混合（查询+下单） | 以上 + `POST /orders` | 读写 | 两个独立线程组，模拟混合负载 |
| 并发下单 | `POST /orders` | 写 | 集合点同时下单，验证库存一致性 |
| 功能正确性 | JUnit `BookingConcurrencyTest` | 写 | 50 并发抢 10 张票，成功数必须等于 10（H2 内存库） |

不纳入本期：支付、退票压力（退票只做功能与并发正确性验证）、多节点集群。

## 4. 测试数据与参数化

`perf/00_perf_seed.sql` 初始化，`perf/01_perf_reset.sql` 每轮复位：

| 数据 | 内容 |
|------|------|
| 用户 | `perf01` ~ `perf20`，密码统一 `Pass123` |
| 线路 | 5 条：北京南↔上海虹桥、广州南→深圳北、成都东→重庆北、武汉→长沙南 |
| 席别/价格 | 每条线路 二等座 / 一等座 / 商务座，价格不同 |
| 座位 | 5 条线路 × 3 席别 = 15 行 `train_seats` |
| 库存 | 二等座 1000、一等座 200、商务座 50 |
| CSV | `perf/data/users.csv`、`routes.csv`、`booking.csv` |

参数化：

- `scenario-query.jmx`、`scenario-mixed.jmx` 用 `CSV Data Set Config` 读取用户/线路/座位，`ignoreFirstLine=true`
- **历史报告的采集口径（已修复）**：报告数据采集时 CSV 是 `shareMode=thread`（每线程各自打开文件、指针从第 1 行开始）。`users.csv` 放在 `Once Only Controller` 里、登录只读一次，所以当时所有线程都读第一行 `perf01`；`booking.csv` 放在单圈下单组里，10 个线程也都读第一行 `perf01 / 9001`。
- 2026-11-09 已把 `users.csv` / `booking.csv` 改为 `shareMode=group`（组内共享指针，线程依次取不同行）；10 线程实测登录账号为 `perf01`–`perf10`，错误率 0%。`routes.csv` 保持 `shareMode=thread`，每线程在循环内轮换 5 条线路。
- `load-test.jmx` 固定 `alice01` + “北京南→上海虹桥”单线路，用于隔离 BCrypt 成本；它**不做**多用户参数化，不能当多用户登录场景

**数据代表性**：修复后 10 线程会分流到 10 个账号、10 个座位；但数据规模仍只有 20 账号 / 5 线路 / 15 座位，历史报告的容量数字仍是单账号口径。要做容量结论，应扩到 200+ 账号、20+ 线路、1 万+ 座位后复跑。

## 5. 场景设计

### 5.1 阶梯加压（查询）

登录一次（`Once Only Controller`），之后在 `Loop Controller` 中循环查询；先跑 10 并发 5 分钟基准，再依次 20/50/100/200，每级 5 分钟，ramp-up 5 秒：

| 阶段 | 基准 10 | 20 | 50 | 100 | 200 |
|------|---------|----|----|-----|-----|
| 线程数 | 10 | 20 | 50 | 100 | 200 |
| 时长 | 5min | 5min | 5min | 5min | 5min |

观察 TPS 与 P95 曲线，找 TPS 不再上升、响应时间开始快速上升的拐点。

### 5.2 混合场景（查询 + 下单）

`perf/scenario-mixed.jmx` 两个独立线程组：

| 线程组 | 并发 | 行为 |
|--------|------|------|
| 查询用户 | 50 | 登录一次，循环查询 |
| 下单用户 | 10 | 延迟 5 秒启动，登录后集合点同时下单 |

持续 60 秒，观察混合负载下的 TPS、P95 和下单成功率。60 秒是短跑，只用于功能/混合行为验证，不作为容量数字。

### 5.3 登录+查询（对比场景）

每次迭代都清 Cookie 并重新登录，用 `perf/load-test.jmx` 跑 10/50/100/200 线程（各 10/10/5/5 圈）和 50 线程 × 100 圈持续负载，用于量化 BCrypt 的代价。

- 固定单账号 `alice01`、单线路，避免账号/线路差异干扰 BCrypt 对比；
- 1 次迭代 = 3 个主请求，事务/秒 = TPS ÷ 3；
- 10/50/100/200 短跑含 5 秒 ramp-up，只有 50×100 圈的持续场景是稳态。

### 5.4 并发正确性（JUnit）

`BookingConcurrencyTest`：余票 10 张，50 个并发请求，断言成功 10 单、40 个“余票不足”、库存 0、订单 10 条；退票后库存回补，重复退票被拒绝。

> 该测试使用 H2 内存库（`@ActiveProfiles("h2")`），不覆盖 MySQL 行锁/隔离级别；MySQL 写并发另需补场景。

### 5.5 性能剖析（JProfiler）

在应用已启动（MySQL 模式、8080）的前提下，用 JProfiler 16.3 本地 Attach 到
`TrainTicketApplication`，CPU sampling 5 ms，在 JMeter 施压期间采样：

| 项 | 配置 / 产出 |
|---|---|
| 采样模式 | CPU sampling，5 ms |
| 压力 | 50 线程 × 300 圈登录+查询，约 5 分钟，错误率 0% |
| 快照 | `docs/profiler/login-5min.jps` |
| CPU 调用树 | `docs/profiler/cpu-calltree.html`，`HTTP: /login` 占 92.1% |
| 热点明细 | `docs/profiler/cpu-hotspots.csv`，`BCryptPasswordEncoder.matches` 占 91.2% |

操作步骤见 `docs/JMeter与JProfiler操作手册.md`。纯命令行导不出 Telemetry 曲线，
需要实时 CPU/内存曲线时用 GUI 会话现场录制并截图。

## 6. 断言与执行规范

- 登录断言：响应体包含“车次查询”
- 查询断言：包含“查询结果”，且不包含“没有查询到符合条件的车次”
- 下单断言：包含“购票成功”
- HTTP 4xx/5xx 由 JMeter 默认判为失败，避免错误页被当成功
- 正式压测用 `-n` 非 GUI，**不启用 View Results Tree / 聚合报告等 GUI 监听器**，只保留 JTL 和 HTML 报告

**TPS 口径**：

- 查询场景：1 次业务 = 1 个 `POST /trains/search`，TPS = 请求/秒；
- 登录+查询：1 次业务 = 3 个主请求，另列事务/秒 = TPS ÷ 3；
- 混合场景：全部主请求/秒；
- 跨场景比较必须用同一口径，不能拿登录场景的 147 直接对查询场景的 1485。

## 7. 指标与通过标准

| 指标 | 说明 | 通过标准 |
|------|------|----------|
| 错误率 | 断言失败 / HTTP 异常占比 | < 0.1% |
| 平均响应时间 | 所有主请求平均 | < 500 ms |
| P95 响应时间 | 95% 请求不超过 | < 1000 ms |
| TPS | 查询=请求/秒；登录+查询=事务/秒；混合=主请求/秒 | > 200 |
| CPU 使用率 | 应用进程 CPU（16 核总量） | 稳定 < 80% |
| 数据一致性 | 库存 + 订单数 | 不超卖、不丢单 |

执行时同时开：

- 应用：`-Xlog:gc`（排除 4～5 秒毛刺）
- JMeter：另开窗口采 JMeter PID 与整机 CPU（区分客户端/服务端限制）
- MySQL：`slow_query_log=ON`、`long_query_time=0.1`（不要用 10s，否则 100ms～10s 的慢 SQL 全部漏掉）

执行前确认（对应 PPT 第 16 页 5 项）：

| 检查项 | 本轮情况 |
|--------|----------|
| 压测环境与生产隔离 | **未隔离**：压测机、应用、MySQL、JMeter 同机；结果偏保守，报告已注明 |
| 压测时间已通知相关团队 | 课程作业，无外部团队；生产压测需提前通知 |
| 服务器监控已开启 | `monitor_resources.ps1` + JFR + MySQL 状态 |
| 测试数据可以恢复 | `01_perf_reset.sql` 复位订单/库存/车票日期；`00_perf_seed.sql` 可重建 |
| 日志级别不会写爆磁盘 | JMeter 用 `-j` 指定日志；应用未开 DEBUG；复测再加 GC 日志 |

## 9. 负压（限流/降级）预案

- 登录限流：`/login` 单实例限制请求速率，超限返回 429 + `Retry-After`
- CPU > 80% 或 P95 > 1s 时，降级非核心功能（管理后台统计等），优先保障查询/下单
- 登录超时/失败率超阈值时熔断，前端提示稍后重试
- 车次/站点等低频数据加缓存；查询可走只读副本
- 超容量先扩容（多实例 + Redis Session），再放开并发

## 10. 风险与约束

- 压测机和被测应用同机，JMeter 自身占用 CPU；本轮没有单独采 JMeter/整机 CPU，结果偏保守，且无法区分客户端/服务端限制
- 登录使用 BCrypt（cost=10），是高 CPU 操作，会成为登录场景的主要瓶颈
- HikariCP 默认 10 个连接；2026-10-28 的 A/B 把 pool 扩到 30，50 线程稳态 TPS 1471.6→1573.4（+6.9%）、100 线程 1503.8→1590.7（+5.8%），**连接池不是平台期主限制器**；之前“10 连接 ≈ 1483 TPS”只是数字巧合
- 同机 JMeter 客户端是最可能的剩余限制器；下一轮需采 JMeter 进程 CPU/整机 CPU，或换第二台压测机/分布式压测
- 数据规模小（20 账号 / 5 线路 / 15 座位），且全部可缓存，容量结论偏乐观
- 混合场景只有 60 秒，且与阶梯场景执行时间不同（10-26 vs 10-27），两者 50 线程结果相差 2.7 倍，绝对 TPS 不可直接比较
- `thymeleaf.cache=false` 是开发配置，模板解析会增加 CPU，压测结果偏保守
- 单机单实例，结果不代表集群容量
- JUnit 超卖测试运行在 H2 上，不覆盖 MySQL 行锁

## 11. 资源监控与报告结构

资源监控：

- `keep_awake.ps1` 防止压测期间机器睡眠（否则 5 分钟档会被拉长、出现假超时）
- `monitor_resources.ps1` 采样应用 JVM、mysqld 的 CPU/内存和磁盘 IO；名义 2 秒/点，实际约 4.6 秒/点，阶段切换处有 7～15 秒空档
- `analyze_resources.py` 生成 CPU/内存曲线和摘要
- `analyze_timeseries.py` 从 JTL 生成 TPS/错误率时间曲线
- 数据库侧：`slow_query_log=ON`、`long_query_time=0.1s`，压测前后对比 `Slow_queries`、`Questions`、`Threads_connected`、`Innodb_row_lock_waits`（本轮报告实际使用的是 10s 阈值，只能证明没有 >10s 的 SQL）
- `perf100.jfr` + `samples.txt` 生成 JFR 火焰图；JProfiler 快照/调用树/Hot Spots 见 `docs/profiler/`；IDEA Profiler 截图是可选的交叉验证
